### 1. 什么是Agent评测
**Agent评测，就是通过一组任务，检查Agent能否正确、稳定地完成工作，并找到失败的原因。**

例如，一个天气查询Agent，需要理解用户问的是哪个城市，调用天气工具，再根据查询结果回答。评测需要检查这条执行链路，同时关注耗时、费用和异常处理。那么如果想要评测这个Agent，我们需要关注**结果、过程、效率和安全**四个方面。

评测最直接的用途是帮助我们比较版本、发现问题和防止功能退步。修改提示词、更换模型或者调整工具之后，可以用相同的任务重新测试，看看哪些地方改善了，哪些地方受到了影响。

例如，模型换成便宜的版本后，回答速度提高了，但经常把“杭州”传成“杭州市西湖区”。评测能够把这种变化记录下来，帮助我们判断这次修改是否值得保留。

### 2. 评测分类

按照**检查范围**来划分的话，可以分为

- **组件评测**：检查某个函数、工具、检索模块是否正确
- **过程评测**：工具选择、参数传递、执行顺序和状态更新是否合理，可以帮助我们定位中间环节的问题
- **端到端评测**：帮助我们判断从用户提出要求到任务结束，整体是否成功

按照**运行场景**划分的话，可以分为

- **离线评测**：用提前准备好的任务集进行评测
- **在线评测**：在真实运行的任务和用户反馈中评测

按照**评测目的**划分的话，可以分为

- **回归评测**：以前能够完成的任务，现在是否依然能够完成
- **能力评测**：面对更复杂的任务，当前系统能够做到什么程度

### 3. 如何评测

首先需要准备评测任务，再选择合适的评分方法。常见的判分方法有：
- 程序判分：使用断言、规则、测试或状态检查
- 模型判分：让另一个模型按照明确标准评价
- 人工评审：由开发者、用户或领域专家判断
实际的评测中通常会将这些方法组合起来使用。

一条评测任务至少需要讲清楚输入、运行环境和成功条件。对于订票、修改文件等实际任务，不仅要关注 Agent 是否输出了理想答案，还需要检查操作后的实际状态。例如，Agent 回复“预订成功”之后，系统中应当确实存在对应的订单。

#### 准备评测集
评测集是一组提前整理好的测试任务，需要覆盖正常需求和容易出错的情况。每个任务都需要制定输入、运行条件和成功标准。开发中遇到的错误也可以保留下来，成为后续修改时需要重新检查的测试任务。

#### Trace
Trace是一次任务的执行记录，通常包含模型调用、工具名称、工具参数、返回结果、错误和耗时。
例如，用户询问杭州天气，最终却得到了北京天气，可以沿着记录逐步检查：

```
用户输入：查询杭州天气
工具调用：get_weather(city="北京")
工具返回：北京，晴，20℃
最终回答：北京今天晴，20℃
```

这份记录表明，错误已经发生在工具参数生成阶段。模型后续准确使用了工具结果，但整个任务没有完成用户的要求。


#### Rubric

然而，在实际的Agent应用场景中，如何去判断Agent的回答是否“高质量”？这很难由主观进行判断，或者说用主观来判断很难建立起一套稳定的评测体系，所以需要考虑将其拆分成具体的条件进行评判。

依旧以天气查询 Agent 为例，天气查询任务可以这样设计，下面的数据专门用于测试：
```
用户输入：
查询杭州当前天气，并告诉我要不要带伞。

天气工具返回：
城市：杭州
天气：小雨
温度：18℃

成功条件：
调用天气工具时，城市参数为杭州。
回答中的天气和温度与工具结果一致。
根据小雨天气给出带伞建议。
接口失败时说明查询失败，不编造天气数据。
```

这种明确的检查条件就叫作 **Rubric，可以理解为具体的判分规则**。

#### 常用指标
|指标|通俗解释|示例|
|---|---|---|
|任务成功率|成功完成的任务次数占总运行次数的比例|100 次运行中成功 82 次，成功率为 82%|
|工具使用正确性|是否选对工具、传对参数、正确使用返回结果|查询杭州时有没有传入杭州|
|回答正确性|回答中的事实是否正确|温度有没有报错|
|有据性|回答中的信息能否从提供的资料或工具结果中得到支持|接口只返回天气，却额外编造了空气质量|
|异常处理能力|接口超时、数据缺失时能否合理处理|超时后提示失败或按规则重试|
|耗时|用户需要等待多久|平均耗时，以及 P95 耗时|
|成本|完成任务需要多少资源|Token 数、API 费用、工具调用次数|
|安全性|是否遵守权限和操作限制|未经确认有没有执行删除操作|

P95 耗时表示约 95% 的任务耗时不超过这个值，有助于发现平均值掩盖的缓慢请求。衡量成本时，还可以计算“总运行费用 ÷ 成功任务数”，把失败尝试消耗的费用也考虑进去。

**Agent 具有随机性，因此同一个任务通常需要重复运行。** 两个经常出现的指标是：

- **pass@k**：同一个任务尝试 k 次，至少成功一次的概率，适合允许多次尝试并筛选结果的场景。
- **pass^k**：同一个任务连续进行 k 次独立试验，全部成功的概率，更关注稳定性。

实际开展评测时，可以先收集常见任务和已有的失败案例，给每个任务写判断任务成功的条件，再选择程序、模型或人工评分。运行时记录工具调用、返回结果、耗时和费用，对存在随机性的任务重复测试。修改 Agent 后使用相同条件重新评测，分析失败原因，并将新发现的问题补充进评测集。

### 4. 评测工具
#### Ragas

Ragas 是一个开源的 AI 应用评测框架，提供现成的指标，帮助开发者评测 RAG 和 Agent。

例如，评测一个先检索资料再回答的 RAG 系统时，可以将用户问题、检索到的资料和模型回答交给 Ragas，按照所选指标补充参考答案，再检查：

- **上下文召回率（Context Recall）**：检索到的资料是否覆盖了回答问题所需的信息。
- **上下文查准率（Context Precision）**：检索的结果是否有用，有用内容是否排在前面。
- **忠实度（Faithfulness）**：模型回答中的事实是否能从检索资料中得到支持。
- **事实正确性（Factual Correctness）**：模型回答中的事实是否符合参考答案。


### 5. Q&A

**1. 模型每次回答都不一样，怎么判断对错？**

可以提前写好评分规则，检查回答是否满足任务要求。比方说对于天气任务，“杭州小雨，18℃，建议带伞”和“杭州目前 18℃，有小雨，出门带把伞”两种不同的措辞，检查回答中的城市、天气和温度是否与工具结果一致，以及是否给出了带伞建议。只要满足这些条件，不同的措辞都可以通过。

**2. Agent 必须按照参考步骤执行吗？**

不一定，只对必要步骤和必要顺序作要求。例如，扣款前必须获得确认，但两个互不依赖的查询通常可以交换顺序。LangChain 的 AgentEvals 提供严格匹配、无序匹配和部分轨迹匹配，正是为了适应不同要求。[AgentEvals](https://github.com/langchain-ai/agentevals)

**3. 工具请求成功，是否意味着任务成功？**

还需要检查请求参数、返回数据和后续使用情况。HTTP 请求正常返回，但城市查错了，或者 Agent 把返回温度读错了，任务依然失败。

**4. 评测时应该使用真实 API，还是模拟数据？**

可以分别安排。固定返回的数据适合比较版本，也方便稳定复现超时、缺字段等情况，真实 API 测试适合检查鉴权、网络和接口兼容性。报告中需要说明使用了哪种环境，并将接口故障与 Agent 的处理错误分开记录。

**5. 能完全相信模型裁判吗？**

模型裁判也会误判，可能偏好更长的答案，或者受到答案排列顺序影响。可以先准备人工审核过的样本，检查它会不会放过错误答案、误判正确答案，再决定哪些评测交给它执行。

**6. 离线分数提高了，就一定适合上线吗？**

还需要观察真实用户的任务完成情况、使用体验和成本。评测集可能漏掉新需求，测试环境也可能与实际环境不同。美团白皮书 FAQ 强调，离线回测负责检查已知能力是否退步，真实效果还需要通过线上观察和适当的 A/B 实验验证。

**7. 分数下降了，是否一定需要更换模型？**

应该先查看执行记录，定位失败发生在哪里。工具接口异常、检索资料缺失、上下文丢失和评分规则错误，都可能影响结果。确认原因之后，才能选择修改提示词、工具、上下文管理或模型。
